# 开发规范

沿用 Radish 系列的单维护者串行节奏、明确边界、正式文档来源和风险匹配验证。流程服务真实交付，不为普通小切片增加无收益的分支、平台或文档仪式。

分支、PR、CI 和远端策略以[仓库治理](../governance/repository-governance.md)为准；工作区、执行授权与交接以[协作规则](../governance/agent-collaboration.md)为准。本篇维护实现、版本和验证原则。

## 1. 日常任务

1. 查看 Git 状态、分支及任务相关的最少文档。
2. 说明目标、输入、影响范围和完成条件，区分既有用户修改。
3. 在已授权范围内推进完整纵向切片，覆盖主路径与对应失败情况。
4. 按风险验证，更新最近的正式来源与必要当前状态。
5. 精确暂存、提交和交接，只报告实际证据。

用户对当前任务的明确指令优先，已授权动作不重复确认。若新增决定实质改变账务、加密、公共协议、许可或外部影响，再说明影响并确认。仓库权限和系统沙盒权限分别处理。

## 2. 分支、提交与远端

```text
普通串行开发 -> dev -> master PR -> master -> dev 回流
按需隔离     -> topic/worktree -> dev -> master PR
```

普通任务直接在 `dev`，隔离按需；稳定晋级经 `master` PR 后回流。Conventional Commits 使用用户身份，无 AI 署名。远端模板不证明保护已经配置，合并不自动授权发布。具体分支角色、合并方法、回流命令、审批与启用步骤统一维护在[仓库治理](../governance/repository-governance.md)。

## 3. 文档职责

| 材料 | 职责 |
| --- | --- |
| README | 定位、核心边界和导航 |
| AGENTS / CLAUDE | 跨任务、跨阶段、启动即需知道的约束 |
| 正式专题 | 产品、领域、架构、同步、加密、部署与格式 |
| ADR | 关键决定、替代方案、后果及冻结条件 |
| current | 实际阶段、证据入口、下一步、临时停止线 |
| devlog | Asia/Shanghai 月度历史与复核记录 |

改变正式规则先改专题，避免多个“当前真相”。根协作文件必须逐字一致，不塞批次编号、日期、机型清单或临时门槛。首次正式文档建立后，聊天稿为历史材料。

## 4. 代码与边界

- 直观命名、早返回、明确类型和浅职责，避免空 wrapper / factory / manager。
- 单个源码接近 1000 行时评估按真实职责拆分，原则上不超过 1500 行；目录不过度嵌套。
- 优先使用对应语言 / 框架惯例、明确类型、结构化错误、标准库和直接函数；不通过字符串标记、隐式全局状态或动态魔法绕开契约。
- 只有真实重复、安全隔离或稳定契约需要时才抽象。第一版不提前建立通用同步 SDK 或统一身份平台。
- Rust 为账务、DB、密钥、同步真相，Flutter 调用并呈现，Go 只处理可见授权和密文事务。
- FFI 必须固定编码、所有权、释放、线程、取消、错误与版本，不能让 panic / 异常穿过未定义边界。
- 金额类型、错误码、envelope、兼容范围与共同样例单一来源；不得每种语言各自猜测。
- 新依赖说明用途、版本、维护、许可、供应链和替代方案，再按授权引入；不顺带升级工具链。
- 引入工程时固定正式工具链和 lockfile，CI 与本地复用检查入口；是否联网下载、更新锁定依赖与安装系统库分别说明。理论平台支持不能替代实际移动端验证。
- 错误保留原因，不以空数据、重建文件、默认成功或无限 fallback 掩盖损坏。
- 确需兼容或恢复 fallback 时，说明触发条件、可观察状态与停止线；不得静默改变信任模式或扩大权限。
- 生成代码、schema 与 fixture 记录生成入口、输入和版本，并与正式来源一致；关键结果使用独立期望或复核路径，避免实现自证。
- 默认中文工程说明，技术标识保留原文；新增文件 / 目录 / 稳定标识优先英文并沿用已有惯例，文本格式以 `.editorconfig` 为准。

## 5. 版本

沿用日历版本 `vYY.M.RELEASE`，开发 / 测试渠道可附 `-dev`、`-test`；具体发行标签只有实际发布任务才创建。

根 `version.json` 为产品版本的手工真相源：

- `schemaVersion`：版本文件自身格式。
- `productVersion`：不含前导 v 的产品日历版本。
- `flutterBuildNumber`：移动端构建序号，发行构建必须单调增加。

manifests / 构建产物从该文件同步，不维护多个独立真相；仓库检查强制核对 Cargo workspace 与 Flutter manifest 的镜像值。规划值和合成实验包均不代表已有稳定产品发行。

产品版本、协议主版本、envelope / 业务 / 备份 schema、DB migration、FFI ABI 和 key epoch 各有用途，不能互相替代。金额或密码语义的兼容变更必须单独设计。

## 6. 验证分层

| 改动 | 最小相关验证 |
| --- | --- |
| 文档 / 治理 | 仓库检查，加变更相关术语 / 范围编号与正式边界复核 |
| Rust 账务 | fmt、check、相关 test / clippy、数值共同样例 |
| Rust 存储 / 同步 / crypto | 相关边界测试、故障注入、格式 / 算法向量、并发 / 重启 |
| Go | gofmt、相关 test / 静态检查；事务改动使用真实 PostgreSQL |
| Flutter / FFI | dart format、analyze、相关 test、两端 build 与真实桥接 |
| 系统密钥 / 生命周期 | 真机正常、取消、拒绝、失效、重启与后台状态 |
| 阶段 / 发布 | 聚合检查、双端主路径、自部署 / 官方目标、升级和独立恢复 |

不为低影响文案改动跑全部业务检查，也不为 implementation mirror 写无意义测试。每项测试要证明业务结果、边界或故障恢复，静态检查不替代真实流程。

仓库检查、文档与文本定向入口的实际命令和覆盖见 [scripts/README.md](../../scripts/README.md)。检查清单包含未跟踪文件，避免普通 `git diff --check` 的盲区；PR 使用 base / head 的真实提交范围，验证合并候选的文件树。

语言实现首次进入时同步建立真实定向入口与 CI 组件；仅治理的门禁会阻断没有对应检查的 Rust / Go / Dart 工程。金额与转账至少验证边界整数和事务中断；同步 / 删除至少验证重复提交、并发、重启与旧设备；crypto / 导入 / 归档覆盖认证失败、资源界限与不完整恢复；这些证据不由文档或检查器回归替代。

移动核心实验的模块、FFI 契约、锁定工具链、生成代码与两端复现命令见[实验说明](mobile-core-prototype.md)；M0 的正式退出条件见[验证矩阵](mobile-core-validation.md)。宿主 CI、模拟器运行与真机目标构建分别记录，不能互相替代。

## 7. 数据、许可与执行

仅使用合成账务、虚构身份和脱敏诊断。真实账单、用户目录、密钥、恢复秘密和生产实例不能因开发方便被读取、导入、截图或发布。

安装依赖、启动长服务、操作系统权限 / 密钥链 / 证书、网络部署和远端写入按实际授权执行；授权只覆盖已说明目标和影响，工作失败不自动扩大范围。

不提交第三方参考截图、品牌元素、未经授权素材、DB / 归档或证据目录。第三方 notices 真实引入时建立，源码可见不免除第三方许可义务。

引入第三方代码、依赖、字体、图标、示例或资产时登记来源、版本、许可证与必要归属；公开可访问不等于可自由再分发。生成物、缓存、本地状态和验证证据按仓库忽略及交付规则处理，不能混入精确暂存路径。

## 8. 交付与证据

交付说明最终行为、范围、实际验证、未验证面和必要恢复路径。记录 fixture、模拟器、真机、生产目标各自证据，不能跨范围外推。

功能存在、安装包能启动、服务可连接、端到端流程通过、安全评审通过是不同结论。公开 MVP 按 R01–R12 与 T01–T23 的真实证据晋级。
