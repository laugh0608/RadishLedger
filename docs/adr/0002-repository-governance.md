# ADR-0002 协作与仓库治理基线

状态：已接受；远端应用与运行证据单独记录。

日期：2026-10-12（Asia/Shanghai）。

## 背景

正式产品规划已经建立，项目所有者要求参考 Radish、RadishMind、RadishCatalyst、RadishFlow、RadishAxiom，提炼通用底层并形成 RadishLedger 自己的规则。工作范围为治理资产和实际仓库检查，继续保留不编写业务代码的边界。

五个项目的不同业务、语言栈和历史基线不能整体迁入。它们一致的单维护者节奏、分支闭环、稳定聚合门禁和证据边界适合作为本项目原则。

## 参考与取舍

阅读来源为各仓库根协作文件、`.github/rulesets/README.md`、分支治理 ADR，以及对应协作 / 治理专题和代表 workflow；不以本地模板推定这些仓库当前的远端状态。

| 参考项目 | 提炼的通用经验 | RadishLedger 的取舍 |
| --- | --- | --- |
| Radish | 风险匹配本地验证、稳定聚合检查、专题与当前状态分离 | 保留原则；不带入 .NET / Web、历史卫生预算或部署脚本 |
| RadishMind | `dev -> master -> dev` 闭环、组件结果严格汇总 | 重新编写轻量检查；不带入平台、工作流业务和数据库门禁 |
| RadishCatalyst | 单维护者不强制日常 PR、轻量治理可先于业务 | 建立真实文档 / 配置检查；不带入 Godot、素材和存档规则 |
| RadishFlow | 保留 merge 拓扑、回流先快进后普通 merge、验证不跨平台外推 | 结合未来移动 FFI；不带入 COM、求解器、安装与 Windows 门禁 |
| RadishAxiom | 短根入口、治理专题路由、机器契约与证据边界 | 全文一致的根入口和配置契约；不带入证明状态、Checker 或 benchmark |

## 决定

1. 普通串行任务在 `dev`；只有外部贡献、并行写入、隔离价值或用户要求才建主题分支 / worktree。
2. `master` 为远端默认稳定主线，PR 晋级；hotfix 经 PR 后也必须回流 `dev`。
3. 允许 merge / rebase、禁用 squash；阶段 PR 优先 merge commit。回流先快进，否则普通 merge，禁止共享历史重写。
4. 单维护者的 `dev` 不设强制保护；PR 检查目标为 `dev` / `master`，普通 push 与 tag 不触发全量 CI。
5. `master` 要求严格的 `Candidate Quality` 与已解决会话，approval 为 `0`，不要求 CODEOWNERS / 线性历史 / 签名；管理员仅 PR 内有例外能力。
6. 仓库内模板声明目标，真实远端读回证明已配置；启用前先完成分支和真实 context 引导，更新已有 Ruleset 而非重复创建。
7. 从本项目重新编写 Python 标准库检查器，覆盖未跟踪文件、文本、文档链接、JSON、根入口、治理契约、PR 提交与 diff。检查器具备合成负向回归。workflow 以 JSON 为单一手工来源并显式生成常规 YAML，同时检查来源语义与生成文件逐字一致；这是首次远端引导时对 workflow 表达方式的补充，不改变门禁政策。
8. 仓库门禁只检查真实已有资产；首次语言实现必须接入真实质量组件，文档门禁不能冒充产品验收。
9. 保留既有源码可见许可和个人自部署权利；账务、密钥、同步、删除、恢复和 FFI 的专门风险进入 PR 与协作规则。

## 替代方案与代价

所有任务强制主题分支 / PR 会增加单维护者成本，保护日常 `dev` 也会阻断直接开发与回流；形成稳定多人维护后再评估。

只写规则、不实现检查无法及时发现配置漂移；复制已有检查器则带入无关栈和历史例外。因此选择无第三方依赖的小型本地 / CI 共用入口，并验证其拒绝行为。

只允许线性历史会与长期分支的 merge 闭环冲突；全局禁止 rebase merge又超过既有习惯。因此保留两种方式，明确阶段晋级优先 merge 和回流语义。

固定 Action SHA 降低引用漂移，但 runner 镜像、Git 和 Python 没有逐项固定，不承诺逐字节可复现构建。新增依赖、真实发行与多人评审需要独立设计。

## 验证与演进

验证仓库入口、文档链接、配置契约及合成拒绝用例；无提交工作区和临时 Git 仓库各取证。实际结果进入月度 devlog 与 current。GitHub 尚未应用的设置不算远端通过。

出现真实 Rust / Go / Flutter 工程时，接入对应检查和共同契约样例；真实 PostgreSQL、双端、部署、升级与恢复的阶段证据按现有开发规范取得。稳定多人评审出现后再提高 approval、评估 CODEOWNERS 和 `dev` Ruleset。
