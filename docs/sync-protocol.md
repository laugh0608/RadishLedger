# 多端同步与连接边界

基线为对象级增量、条件更新、幂等提交和保留冲突。第一版不做通用 CRDT、不按设备时间决定胜负，不以整库文件覆盖。

本文件定义语义草案；HTTP 路由、准确字段编码、限制和兼容窗口在 M0 / M2 的对应 ADR 与契约中冻结。

## 1. 实例与同步域

一个活动 Vault 对应一个实例中的同步域。URL 可变化，实例身份不能只由字符串相等判断；实例 ID 也不能单独替代可信 TLS。相同邮箱或对象 ID 不授予跨实例访问或合并权限。

凭据、设备、密钥包装、generation、游标、outbox、冲突和恢复状态共同绑定实例 / 同步域。纯本地操作在首次启用同步时显式绑定，不能自动塞进新域的队列。

连接步骤：

1. 校验 URL，生产必须 HTTPS；拒绝含凭据 URL 和不安全跨主机重定向。
2. 用有界无凭据请求发现实例身份、协议范围、能力和注册状态。
3. 显示实际主机与兼容结论，再在目标实例认证。
4. 创建新同步域或选择并解锁已有域；本地与远端都有数据时走显式选择 / 导入，不覆盖。
5. 完成域绑定、密钥可用性及数据核对后才允许同步。

切换前停止旧 runtime、保留未完成操作和已知提交身份，再创建新的 runtime generation。每个响应携带本机请求所属的连接上下文，迟到回调只能归属旧任务；不能污染新域。

保存地址不等于授权、解锁或同步成功。选择官方端点不授权账务进入其他 Radish 服务或模型。

## 2. 身份与公开 envelope

候选外层包含协议 / envelope 版本、实例和域绑定、随机对象 / 操作 / 修订 ID、前置版本、密钥 epoch、nonce 及密文。业务类型、金额、日期、名称、备注和引用内容进入密文。

服务端排序 cursor 与业务修订 ID 分开。服务分配的 cursor 是传输元数据，不冒充客户端 AEAD 已认证的内容。对象身份、客户端修订、parent、epoch 和语义标记等不可变外层必须以确定性编码绑定 AAD。

操作内容一旦开始发送便不可变。幂等键按账号 / Vault / generation / operation ID 隔离；同键不同内容拒绝。请求 digest 与确认结果保留在对应范围内，不能仅按 HTTP 重试次数去重。

服务端删除标记与加密对象中经过认证的删除意图相互核对。未知或无法认证的删除不能清除本机记录。

服务能看见 ID、长度、时间、访问关系、版本与批次规模；这些属于元数据，不能宣传完全匿名。

## 3. 原子提交与增量序号

一个操作可包含多个对象和前置条件。转账本身为单一交易 payload；需要同步账户 / 类别等引用时，按依赖顺序或原子批次发送。

同一服务端事务内：

1. 校验会话、归属、配额、generation 和操作内容界限。
2. 检查幂等身份，已提交原操作返回原结果。
3. 对前置版本进行 CAS；任一前置条件失败则整批不提交。
4. 写密文对象 / 删除状态、追加变更流并保存确认。
5. 成功提交后才返回确认。

变更序号必须表示已提交的稳定顺序。不能仅用事务提交前分配的普通数据库 sequence 再按“序号大于 cursor”读取：并发事务晚提交较小序号会漏读。M0 需选择并验证账库级串行序号分配或等价的无遗漏提交顺序方案。

分页固定已提交的上界，原子批次不拆成可独立应用的半批。游标不可仅用修改时间、设备时间或不稳定 offset 替代。

## 4. 客户端循环

1. 本地保存事实、修订与 outbox，返回本机成功。
2. 确认活动域、generation、协议、会话和密钥；拉取稳定范围内的增量。
3. 对 envelope、AEAD、版本链、业务类型和引用进行有界验证。
4. 同事务应用完整批次、更新修订 / 投影及 applied cursor。
5. 按依赖提交 outbox；响应丢失时查询或重试原操作，不能换新 ID。
6. 确认后更新队列；CAS 冲突保留候选，解决后创建基于最新版本的新操作。

已经在发送的内容不能折叠或更改；后续本地修改作为依赖操作排队。尚未发送的候选可在有明确语义的情况下合并，但不得丢掉历史与撤销范围。

第一版遇到无法解密、格式未知或语义非法的完整批次，保留本地事实并暂停该域增量应用，提供具体诊断，不推进 applied cursor。后续若增加隔离继续机制，必须另行定义 received / applied 身份及缺口，不能假装“全部同步”。

## 5. 冲突策略

| 场景 | 处理 |
| --- | --- |
| 不同 ID 的新增 | 独立合并；金额与日期相同不表示重复 |
| 同对象两端修改 | 整体候选冲突，不自动拼字段 |
| 修改与删除 | 保留双方候选与删除修订，明确选择 |
| 转账并发修改 | 整笔选择，双方账户效果同步重建 |
| 归档引用冲突 | 保留事实并提示引用状态，不猜测替换账户 |
| 差额调整与其他新增 | 保留固定差额，提示重新对账 |
| 连续本地编辑 | 维持依赖链，不把修改当新增交易 |

冲突处理默认“选择一个有效版本”。“保留两笔”仅能作为明确创建新业务交易的动作，须展示重复入账风险与余额影响。

第一版无复杂关联退款；未来这种累计业务约束须以真实读集合 / 前置修订构造原子提交，不能由看不见金额的服务器自动推断。

## 6. 删除与旧设备

删除和恢复均为新修订。服务端与客户端保留 tombstone 或等价的防复活身份；回收站内容与防复活标记生命周期分别定义。

第一版不自动压缩删除身份。若以后 GC 变更流或历史，必须定义最低可增量 cursor、全量快照及旧设备重建，不让过旧客户端直接覆盖当前数据。

删除或恢复同样需要 CAS；过期修改进入冲突，不直接重建一个已删对象。全量同步不能以“服务器返回对象缺失”推断本机未同步记录需要删除。

## 7. 备份回滚与客户端重连

运维恢复创建新的 restore generation，并关闭旧提交身份。客户端发现代次变化后：

- 保留本机快照、outbox 和已确认身份；
- 停止旧队列直接重试，进入恢复对账；
- 区分服务器缺失、旧确认、未同步和删除证据；
- 核对后以新操作身份重新提交必要事实。

普通网络错误不生成新 generation。新安装客户端没有此前检查点时，无法仅凭服务器数据证明不存在恶意历史截断；此限制见威胁模型。

## 8. 调度与状态

前台启动、回到前台、保存后和手动刷新触发；两端打开时以有界增量轮询实现首版，失败退避。推送、长连接后置。

锁定后不为后台体验常驻解密钥。平台允许时可处理已加密请求，但默认不能据此承诺完整锁屏收发或实时性；首版主要同步窗口为解锁前台。

状态至少区分：仅本地、未配置、未开放、连接诊断失败、未授权、离线、待同步、同步中、已完成收发、冲突、隔离 / 不支持、恢复待处理。显示待确认数和最后完整循环时间。

有未确认操作、冲突或验证失败时不得显示“所有数据已同步”。本地保存成功与远端提交确认分开文案。

## 9. 兼容与验证

协议主版本、envelope、业务 schema、备份 schema、DB migration 和 key epoch 各自版本化，不以产品 CalVer 替代。

未知关键字段 / 类型、不可兼容加密或失效 epoch 拒绝远端写入；本地数据与待处理候选保留。精确兼容窗口在 M2 冻结，不能仅声称“兼容最新版”。

核心证据包括重复提交、提交后超时、分页并发晚提交、乱序重放、切换迟到响应、删除旧设备、回滚代次及不同账号同 ID。验收编号见[MVP 路线图](mvp-roadmap.md)。
