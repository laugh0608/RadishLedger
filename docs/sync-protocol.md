# 多端同步与连接边界

基线为对象级增量、条件更新、幂等提交和保留冲突。第一版不做通用 CRDT、不按设备时间决定胜负，不以整库文件覆盖。

本文件是 M0-D 语义规格草案，描述可评审的事务边界，不表示同步实现或验收已经完成。HTTP 路由、准确字段编码、限制和兼容窗口在 M0 / M2 的对应 ADR 与契约中冻结。共同输入、独立预期、并发调度和实际验证任务见[同步事务案例](validation/sync-cases.md)；当前进度只见 [current](status/current.md)。

## 1. 实例与同步域

一个活动 Vault 对应一个实例中的同步域。URL 可变化，实例身份不能只由字符串相等判断；实例 ID 也不能单独替代可信 TLS。相同邮箱或对象 ID 不授予跨实例访问或合并权限。

凭据、设备、密钥包装、安全域 / 恢复代次、游标、outbox、冲突和恢复状态共同绑定实例 / 同步域。纯本地操作在首次启用同步时显式绑定，不能自动塞进新域的队列。

连接步骤：

1. 校验 URL，生产必须 HTTPS；拒绝含凭据 URL 和不安全跨主机重定向。
2. 用有界无凭据请求发现实例身份、协议范围、能力和注册状态。
3. 显示实际主机与兼容结论，再在目标实例认证。
4. 创建新同步域或选择并解锁已有域；本地与远端都有数据时走显式选择 / 导入，不覆盖。
5. 完成域绑定、密钥可用性及数据核对后才允许同步。

切换前停止旧 runtime、保留未完成操作和已知提交身份，再创建新的 runtimeGeneration。每个响应携带本机请求所属的连接上下文，迟到回调只能归属旧任务；不能污染新域。

保存地址不等于授权、解锁或同步成功。选择官方端点不授权账务进入其他 Radish 服务或模型。

### 1.1 四种代次与作用域

下列名称是规格符号，不是拟定的网络字段。实现不得继续用一个无修饰的 generation 同时表达它们。

| 概念 | 改变条件 | 不能据此推断 |
| --- | --- | --- |
| `vaultGeneration` | 安全重建创建的新账库安全域；迁移到新实例也建立新域身份 | 改 URL、重试请求或恢复服务器备份不会自动生成新业务账库 |
| `restoreGeneration` | 服务端从旧备份恢复后，在重新开放访问前生成 | 它不是换根钥、业务修订或客户端重连次数 |
| `keyEpoch` | 该安全域的密钥版本，按密钥生命周期决定 | 改 epoch 不隐式授权旧域上传，也不等于撤回旧密钥 |
| `runtimeGeneration` | 本机切连接 / 停止旧 runtime 后创建的新请求上下文 | 它只隔离本机迟到回调，不替代服务端恢复代次 |

提交、确认查询和增量读取的完整上下文记为 `S = (instance, account, vault, vaultGeneration, restoreGeneration)`。账号取自认证主体并核对资源归属，不信任请求中自报的账号。幂等键是 `(S, operationId)`；对象 / 修订也不能脱离实例和域单独寻址。密钥按所属安全域和 epoch 使用，恢复代次变化不自动改变已有密文的认证身份。

`runtimeGeneration` 仅在本机附着于请求及回调；每次落库前重新核对当前活动上下文。更换会话 token 不更换 operationId；重新登录同域后仍对账原操作。恢复代次变化则停止普通重试，按第 7 节处理。restoreGeneration 与账号是否进入具体 AAD、如何认证批次成员关系，在确定性编码评审时明确，不能直接改已有密文的 AAD 后声称仍可解密。

## 2. 身份与公开 envelope

候选外层包含协议 / envelope 版本、实例和域绑定、随机对象 / 操作 / 修订 ID、前置版本、密钥 epoch、nonce 及密文。业务类型、金额、日期、名称、备注和引用内容进入密文。

服务端排序 cursor 与业务修订 ID 分开。服务分配的 cursor 是传输元数据，不冒充客户端 AEAD 已认证的内容。对象身份、客户端修订、parent、epoch 和语义标记等不可变外层必须以确定性编码绑定 AAD。

操作内容一旦开始发送便不可变。幂等键按第 1.1 节的完整上下文隔离；同键不同内容拒绝。请求 digest 与确认结果保留在对应范围内，不能仅按 HTTP 重试次数去重。

服务端删除标记与加密对象中经过认证的删除意图相互核对。未知或无法认证的删除不能清除本机记录。

服务能看见 ID、长度、时间、访问关系、版本与批次规模；这些属于元数据，不能宣传完全匿名。

### 2.1 不可变操作与校验职责

客户端在首次发送前持久化一个有界操作：所属上下文、operationId、全部读前置条件、按确定顺序排列的对象变更及其 envelope。一次重试沿用原 nonce、密文、修订 ID 和前置条件；重新加密、替换 parent 或增删成员都属于新操作。传输层 token、重试计时和连接 ID 不改变操作内容。

请求摘要覆盖上述完整不可变内容，不能只对密文、部分字段或普通 JSON 序列化结果取 hash。字节编码及摘要算法尚待冻结；本轮案例使用可区分的符号内容，不能充当密码向量。客户端需认证对象的域 / 身份 / parent / epoch / 删除语义，并能核对完整批次的成员及绑定，拒绝拆批、拼批或重复成员；采用哪一种 AAD / manifest 构造仍待密码规格评审。

| 边界 | 必须验证 | 无法代替的验证 |
| --- | --- | --- |
| 服务端接收 | 认证和资源归属、上下文、支持的外层版本、大小 / 数量 / 总工作量、ID 唯一性、CAS、幂等身份、写入许可 | 无法检查金额、交易类型、密文内引用或 AEAD 真伪 |
| Rust 客户端接收 | 完整批次及身份、认证解密、支持的业务格式、版本关系、全部业务约束及引用 | E2EE 不能代替服务端访问控制，AEAD 不能证明服务没有隐藏历史 |
| Flutter 展示 | 核心状态和需用户处理的原因、待确认 / 冲突 / 恢复范围 | 不实现另一套合并规则，不用 UI 成功提示替代核心提交 |

同一对象在一个操作中最多有一个目标修订；同一前置对象不能给出矛盾条件。引用必须已被当前客户端验证，或在同批中按完整集合验证后一起发布。只读前置条件也参与 CAS；不能用“本次未写这个对象”为由忽略它。具体上限未冻结前不声称任意大小原子批次可支持。

每个写对象必须有明确且唯一的前置条件，外层 parent 与之相符；不允许隐式无条件 upsert。新修订 ID 在所属安全域内不得重绑定到其他对象、内容或操作；原操作重试由回执处理，换一个 operationId 不能覆盖既有修订。数据库唯一性及客户端认证关系都要验证，不能只依赖随机 ID 碰撞概率。

## 3. 原子提交与增量序号

一个操作可包含多个对象和前置条件。转账本身为单一交易 payload；需要同步账户 / 类别等引用时，按依赖顺序或原子批次发送。

服务端只确认密文事务已提交，不确认明文合法或所有客户端已应用。事务入口先验证会话、归属、完整上下文和有界外层结构；在共享数据库中完成同域竞争的串行判定：

1. 取得域提交控制，并重新核对恢复代次、授权及资源状态，不能只使用排队前的缓存。
2. 查幂等登记；同键不同内容拒绝。相同内容已有终态则返回原结果，不重新执行 CAS 或扣减业务配额。
3. 对新操作核对当前写入许可、epoch 和配额；核对所有前置条件。任一 CAS 失败则整批业务不提交。
4. 成功时一起写对象 head / 删除状态、不可变变更批次、已提交高水位和原确认结果。
5. 数据库事务成功提交后才发送结果；提交期间连接断开或调用超时不能推断已经回滚。

权限撤销 / 账号删除和域恢复必须与写事务有可验证的先后关系；排队期间撤销后，不能凭旧检查继续提交或读回执。已提交操作的重放仍需当前访问权与相同 restoreGeneration，但不因后来域冻结、配额耗尽或写入 epoch 政策变化而变成一次新写入。旧代次的确认只能作为恢复对账证据，不能绕过第 7 节继续普通重试。

变更序号必须表示已提交的稳定顺序。不能仅用事务提交前分配的普通数据库 sequence 再按“序号大于 cursor”读取：并发事务晚提交较小序号会漏读。M0 需选择并验证账库级串行序号分配或等价的无遗漏提交顺序方案。

分页固定已提交的上界，原子批次不拆成可独立应用的半批。游标不可仅用修改时间、设备时间或不稳定 offset 替代。

### 3.1 CAS 与幂等登记候选

前置条件至少区分“从未存在”和“当前 head 恰为指定修订”。tombstone 是存在的 head，不能满足创建的“不存在”条件。编辑 / 删除 / 恢复都比较完整修订身份；同一金额、设备时间或本机递增号不能替代版本身份。对整批先判断条件、后发布全部结果，不返回部分对象成功。

本轮建议将已受理操作的终态分为 `committed` 与 `preconditionRejected`，二者都保存原请求摘要及有界结果；这是待评审的回执策略，尚未冻结公共错误码或存储 schema：

- CAS 失败只提交控制面的拒绝登记，不改变任何业务 head、删除状态或变更高水位。相同原操作重试仍返回该次拒绝；重新拉取和解决后创建新 operationId，不修改原请求后重用身份。
- `committed` 保存该操作的提交位置和修订身份。即使对象后来又被编辑，重试也返回原确认，不返回后来 head 冒充原结果；客户端仍需拉取后续变化。
- 未认证、错误作用域、外层无法有界解析、配额等受理前拒绝，以及未提交的事务中断，不承诺已登记终态。查不到记录只表示查询时不可见，不证明另一个连接中的原请求不会提交；客户端始终保留原内容和身份重试。
- “同键异内容拒绝”的服务端保证从登记成功起成立；客户端从首次发送起即禁止变更内容。不能承诺为任意未认证 / 畸形请求永久预留键。拒绝登记本身须计入独立控制存储配额，满额时拒绝受理，不能先创建无限登记。
- 同一 `S` 内不按短期 HTTP 缓存 TTL 自动删除幂等绑定。后续若回收正文 / 回执，必须仍可判断旧键与原内容、旧操作结果及过期拒绝，另行定义保留期与重建协议，不能让旧重试再次生效。

上述候选具体化“整批不提交”的范围：业务事务无部分效果，不禁止留下明确的拒绝控制记录。失败登记的保留成本和与配额的事务顺序必须在实现前评审；未受理 / 结果未定 / 已拒绝不能合成一个可丢弃队列的“失败”。

另一可评审方案是只保存成功回执；它减少拒绝记录成本，却不能在服务端识别此前被拒绝、尚未绑定的同键异内容请求，重试拒绝结果也可能变化。本轮案例采用前一种较强绑定候选，不把这一取舍当作已接受的公共协议决定。若改选另一方案，必须明确调整保证范围及 S02 / S04 / S24 的预期，而非让实现悄悄弱化它们。

### 3.2 无遗漏提交顺序的数据库候选

M0-D 首个验证候选采用 PostgreSQL 中每个稳定安全域 `(instance, account, vault, vaultGeneration)` 的控制行，行内保存当前 restoreGeneration 和普通事务性整数 `H`。请求的 `S` 必须与锁后读到的当前代次相符；不能因 R 改变而建立互不约束的新旧写锁。`H` 表示当前恢复代次已提交业务批次的高水位，一个业务操作占一个位置，不按对象数占多个位置。所有修改该域的进程使用同一控制行；进程内 mutex 不足以保护多连接 / 重启。

候选事务顺序为：取得 `SELECT ... FOR UPDATE` 域行锁 → 读取锁后的有效代次 / 冻结状态 / `H` → 判定幂等与全部 CAS → 成功时写完整批次 `H + 1`、heads、回执并更新 `H` → COMMIT 后释放。普通回滚不消耗这个事务性位置，拒绝登记不增加 `H`。计数溢出明确拒绝，不能环绕。控制行必须预先随域建立；缺失时不能让并发请求各自建一个“新域”。

不在分配位置后提前释放锁，不用 `SKIP LOCKED` 跳过正在提交的本域，也不在释放控制锁的 savepoint 回滚后继续写。账号级配额 / 撤销若使用额外锁，需统一锁顺序并覆盖相应竞争；域行锁本身不证明账号级安全。死锁、锁等待和数据库重试有界，重试整个数据库事务及原操作，不能接着运行半个事务。

代价是同域写入串行、长批次延长锁等待；持锁期间不执行网络调用或客户端密码工作。跨域能否并行还受账号配额等共享资源约束，必须实测，不能直接公布吞吐结论。其他等价的提交排序方案可以另行比较，但仅提高隔离级别并不能据此宣称预分配 sequence 已成为提交顺序，仍须通过同一晚提交 / 分页案例。

这一选择由现有“同域提交必须有稳定先后”的要求推导，尚未完成真实数据库证明。PostgreSQL 说明普通 sequence 分配不随回滚撤销，Read Committed 的各语句可读到不同提交快照；因此不能用先取号后独立提交或排队前读出的 head 作为该方案的证据。[事务隔离说明](https://www.postgresql.org/docs/18/transaction-iso.html)。行锁持有到事务结束，savepoint 回滚可能释放其后取得的锁，这也是验证必须控制锁生命周期的原因。[显式锁说明](https://www.postgresql.org/docs/18/explicit-locking.html)。引用 18 版文档只解释候选机制，不冻结服务端版本或宣称该方案已经通过。

### 3.3 稳定分页

增量请求绑定 `S`、已应用位置 `A`、本轮固定上界 `U` 和有界页大小。开始本轮读取时捕获已提交的 `H` 为 `U`；之后只读取 `A < position <= U` 的完整不可变批次。`U` 之后的新提交留到下一轮。每页重新检查访问权和 restoreGeneration，不跨代次沿用 token。

单页的代次核对、窗口和批次读取需处于一致的数据库读取边界；不能先检查旧代次、恢复切换后再从新数据读取。若使用分页 token，服务端校验其上下文与原固定上界，不能允许客户端任意抬高 `U` 混入后来的提交；具体 token 编码 / 保护方式待冻结。

- 页面从变更批次本身读取原 envelope，不能 join 当前 head 取出较新正文替代历史批次。本轮验证候选在同代次内不 GC 这些批次，因此无需跨多次 HTTP 请求保持一个长数据库事务来固定 `U`；长期正文保留政策仍须评审，不能拿实验保留方式冒充用户永久历史承诺。
- 页边界只落在完整业务批次之间。合法单批必须在受支持的接收资源界限内；若协商的页预算装不下下一完整批次，返回具体界限错误且不前进，不返回半批或无进度的成功页。准确字节上限及协商方式待冻结。
- 页内位置严格递增、范围和后续位置一致；采用连续 `H` 的候选须检测缺口。缺位置、同位置异内容、跨域 cursor、异常高水位回退都暂停核对，不能猜一个更大的 cursor 跳过去。
- `A = U` 时空页表示“本轮已读到该上界”，不表示永远没有新变化。`A > U` 或上界低于本机已知同代次检查点时不是空账库，而是恢复 / 一致性错误。
- 分页 token 是传输上下文，不是客户端 AEAD 认证的历史证明；过期后从已持久化的 `A` 建立新窗口，保留已经应用事实和未确认操作，不清库重来。

## 4. 客户端循环

1. 本地保存事实、修订与 outbox，返回本机成功。
2. 确认活动域、vaultGeneration / restoreGeneration、协议、会话和密钥；拉取稳定范围内的增量。
3. 对 envelope、AEAD、版本链、业务类型和引用进行有界验证。
4. 同事务应用完整批次、更新修订 / 投影及 applied cursor。
5. 按依赖提交 outbox；响应丢失时查询或重试原操作，不能换新 ID。
6. 确认后更新队列；CAS 冲突保留候选，解决后创建基于最新版本的新操作。

已经在发送的内容不能折叠或更改；后续本地修改作为依赖操作排队。尚未发送的候选可在有明确语义的情况下合并，但不得丢掉历史与撤销范围。

第一版遇到无法解密、格式未知或语义非法的完整批次，保留本地事实并暂停该域增量应用，提供具体诊断，不推进 applied cursor。后续若增加隔离继续机制，必须另行定义 received / applied 身份及缺口，不能假装“全部同步”。

### 4.1 确认、应用和取消分开

本机事实、远端确认与接收 cursor 是三个独立事实。收到本机 operationId 在位置 `P` 的确认，只能更新该 outbox 的确认状态；若尚未应用 `P` 前的其他批次，不能把 applied cursor 直接设为 `P`。后续拉取本机操作的回声时，按身份 / 内容精确去重并保留原修订，不能再次产生交易效果或新的上传意图。

| 本机队列状态（概念） | 进入条件 | 允许的下一步 |
| --- | --- | --- |
| 待发送 | 本地事实与 outbox 已原子提交 | 验证上下文 / 依赖后发送；本地已成功不等待网络 |
| 等待确认 / 结果未定 | 已尝试发送，尚无可核对终态；含超时、断线和取消等待 | 保留原身份 / 原字节，查询或重试；不得当作未提交换 ID |
| 已远端确认 | 回执上下文、operationId、摘要和提交结果均匹配 | 持久化确认，继续完整增量应用；不删除候选历史 |
| 冲突待处理 | 确定的 CAS 拒绝，拉取并验证当前远端版本 | 保留本地意图 / 依赖与远端候选，显式解决后创建新操作 |
| 阻塞 | 权限、格式、资源、epoch 或完整批次校验不满足 | 显示具体原因并保留数据；恢复条件后从原检查点继续 |
| 恢复对账 | restoreGeneration / 安全域发生变化 | 禁止直接重试旧队列，进入第 7 节流程 |

发送后取消、锁定或切后台只能停止等待 / 后续调度，不能撤销已到服务端的提交。落库前的 runtime 上下文核对和停止旧上下文需在同一串行状态边界内完成，不能“先检查后异步写入”留下切换窗口。重开原域时重新对账结果未定操作。

完整远端批次的修订 / 候选、选中版本、投影、去重身份、相关确认以及 applied cursor 在一个本地事务中发布；解密或有界验证可以在发布前准备，但事务内重检引用和本地版本。崩溃只允许完整旧或完整新状态。收到较后的页先不应用，不用排序后跳过缺批；重复已应用批次只在身份 / 内容相符时忽略。

后续本地编辑依赖前次修订：前次结果未定时不改它的正文，不把子操作先送出；前次 CAS 冲突时子链一起保留待解决。服务端不能解密业务引用，客户端不得以服务端 CAS 成功代替引用 / 归档规则验证。

## 5. 冲突策略

| 场景 | 处理 |
| --- | --- |
| 不同 ID 的新增 | 独立合并；金额与日期相同不表示重复 |
| 同对象两端修改 | 整体候选冲突，不自动拼字段 |
| 修改与删除 | 保留双方候选与删除修订，明确选择 |
| 转账并发修改 | 整笔选择，双方账户效果同步重建 |
| 归档引用冲突 | 保留事实并提示引用状态，不猜测替换账户 |
| 差额调整与其他新增 | 保留固定差额，提示重新对账 |
| 连续本地编辑 | 维持依赖链，不把修改当新增交易 |

冲突处理默认“选择一个有效版本”。“保留两笔”仅能作为明确创建新业务交易的动作，须展示重复入账风险与余额影响。

第一版无复杂关联退款；未来这种累计业务约束须以真实读集合 / 前置修订构造原子提交，不能由看不见金额的服务器自动推断。

CAS 拒绝不把输掉的密文作为成功变更追加到服务器流。候选保留的最低保证是：发起端保留未被确认的本地修订、意图及依赖，拉取胜出版本后形成可追踪冲突；不能声称其他设备已收到所有失败候选。候选跨设备传播若成为要求，需独立定义受认证的候选对象与保留方式，不能偷偷把拒绝变成部分提交。

解决操作以最新已验证远端 head 为 CAS 前置，同时在本地记录被处理候选集合。解决期间再有远端修改时，整次解决仍可能失败，原候选与新的本地选择继续保留。选中版本只产生一份账务投影；同一 transfer 的两个账户效果不得分别选择。`A07` 的数值预期用于验证本地候选 / 选择，不能直接视为服务端已经实现多 head 合并。

## 6. 删除与旧设备

删除和恢复均为新修订。服务端与客户端保留 tombstone 或等价的防复活身份；回收站内容与防复活标记生命周期分别定义。

第一版不自动压缩删除身份。若以后 GC 变更流或历史，必须定义最低可增量 cursor、全量快照及旧设备重建，不让过旧客户端直接覆盖当前数据。

删除或恢复同样需要 CAS；过期修改进入冲突，不直接重建一个已删对象。全量同步不能以“服务器返回对象缺失”推断本机未同步记录需要删除。

删除的外层标记必须与认证密文中的删除意图、对象及 parent 一致。缺少可认证删除正文或两者不符时阻塞该批，不先删除本机事实再报告失败。显式恢复以当前删除修订为 parent 生成新修订并重新校验恢复内容；旧删除修订和防复活身份仍保留，不把恢复实现为擦掉 tombstone。曾存在 / 已删除的对象不再满足“从未存在”。

交易 tombstone 只处理对象历史，不能替代账号 / 账库注销控制记录。旧运维备份中的删除控制按[自部署恢复](self-hosting.md#4-运维备份与灾难恢复)重新应用，未完成时不得开放访问。

## 7. 备份回滚与客户端重连

运维恢复创建新的 restoreGeneration，并关闭旧提交身份。客户端发现代次变化后：

- 保留本机快照、outbox 和已确认身份；
- 停止旧队列直接重试，进入恢复对账；
- 区分服务器缺失、旧确认、未同步和删除证据；
- 核对后以新操作身份重新提交必要事实。

普通网络错误不生成新的 restoreGeneration。新安装客户端没有此前检查点时，无法仅凭服务器数据证明不存在恶意历史截断；此限制见威胁模型。

### 7.1 恢复屏障与对账

运维恢复先关闭普通访问，验证备份 / 版本 / 删除控制，再生成不同于历史已开放值的 restoreGeneration 并持久化，失效旧会话，最后开放恢复入口。不能仅从回滚后的 DB 计数器加一来保证从未重用；代次来源、恢复屏障与恢复前检查点的保存位置属于运维实现待验项。若无法证明安全完成，保持关闭，不用旧代次先启动再补标记。

关闭访问必须包含停止新受理、排空或终止原写事务及阻止旧服务进程继续接入，不能只改负载入口后留下旧后台写者。恢复后旧请求仍须在稳定域控制行上重新核对代次；新旧恢复窗口不能各自持有一把互不相干的锁并同时写。

客户端看到新代次后不把旧 cursor 归零后直接上传：先保全本机事实 / 候选 / 删除证据 / 原确认，读取并验证新代次的稳定范围，区分仍存在、服务端回滚丢失、原本未确认和已删除。旧回执证明“曾在旧代次确认”，不证明恢复后的服务器仍保有该事实；旧账库缺少记录也不能解释为用户删除。

对账后需要重新提交的内容使用新操作身份和当前前置条件；是否需要重新加密取决于已冻结的域 / AAD 绑定，不能只改旧 envelope 标签。保留原业务意图及新旧身份关系，不能让同一事实以多个新 ID 自动重复入账。自动可判定的对账规则、不可判定时的用户决策、完整快照格式由 M0-D / M0-E 后续实现契约补齐，本轮不承诺一键自动修复。

恢复后当前传输上下文和备份中保留的原始提交来源必须分开：既有修订、原 envelope 和旧确认不能被改标签成“在新代次重新提交过”。继承的历史如何映射到新代次的读取基线、哪些原始绑定用于认证、哪些仅为当前恢复窗口元数据，须在恢复清单 / 快照契约中明确。该映射未冻结前，只能验证代次变化后的停止与保全，不能宣称已支持从旧备份自动续接新流。

同代次却观察到低于已知检查点的高水位、修订替换或同键异内容，按一致性 / 回滚异常停止；不自行接受为正常新代次。恢复协议约束协作的服务器，不能证明恶意服务器没有隐藏批次或向不同客户端分叉。

### 7.2 迁移冻结与撤销

本节只定义[服务器迁移](data-portability.md#5-服务器迁移)依赖的源域边界，不定义归档格式、目标导入或跨服务分布式事务。

冻结是具备权限的显式控制操作，绑定当前 `S` 和本次冻结身份，与普通写入共用域提交控制。确认冻结时返回该时点稳定 `U`：排在冻结之前提交的操作必须包含在 `U` 内；排在之后的新写拒绝，不出现“已经确认冻结但另一连接继续提交”。已有成功操作可在当前权限 / 代次下查询原确认，不因此新增写入。

冻结与撤销均需幂等及条件身份，结果未定时先查询原控制操作；不能创建新冻结身份掩盖原结果。撤销只作用于仍有效的同一次冻结和同一 restoreGeneration，过期撤销不能解开后一次迁移或恢复屏障。冻结后继续验证到 `U`；目标失败或源端失联时，保留原域、目标暂存和未同步事实，不默认解除冻结或双写。

源恢复代次变化会使原冻结证明失效，重新对账前停止迁移切换。目标开始日常写入后，返回源域需要新的迁移 / 对账，不能靠撤销旧冻结实现跨域回滚。具体控制接口、权限和目标发布格式在后续契约中冻结。

## 8. 调度与状态

前台启动、回到前台、保存后和手动刷新触发；两端打开时以有界增量轮询实现首版，失败退避。推送、长连接后置。

锁定后不为后台体验常驻解密钥。平台允许时可处理已加密请求，但默认不能据此承诺完整锁屏收发或实时性；首版主要同步窗口为解锁前台。

状态至少区分：仅本地、未配置、未开放、连接诊断失败、未授权、离线、待同步、同步中、已完成收发、冲突、隔离 / 不支持、恢复待处理。显示待确认数和最后完整循环时间。

有未确认操作、冲突或验证失败时不得显示“所有数据已同步”。本地保存成功与远端提交确认分开文案。

已有远端确认但增量尚未应用到本轮 U 时，仍不能宣告收发完成。“已完成收发”只表示某次有记录的稳定窗口已应用、当时待确认队列已处理且无已知冲突 / 阻塞，不保证其他离线设备没有新事实，也不把持续变化的服务器描述为永久同步完成。

## 9. 兼容与验证

协议主版本、envelope、业务 schema、备份 schema、DB migration 和 key epoch 各自版本化，不以产品 CalVer 替代。

未知关键字段 / 类型、不可兼容加密或失效 epoch 拒绝远端写入；本地数据与待处理候选保留。精确兼容窗口在 M2 冻结，不能仅声称“兼容最新版”。

核心证据包括重复提交、提交后超时、分页并发晚提交、乱序重放、切换迟到响应、删除旧设备、回滚代次及不同账号同 ID。验收编号见[MVP 路线图](mvp-roadmap.md)。
