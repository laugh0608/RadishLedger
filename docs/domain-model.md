# 账务模型与统计口径

流水修订是账务事实，账户余额、月汇总和分类排行是可重建投影。网络确认状态与业务有效状态分开：本机已提交的候选可以影响本机余额，但未确认或冲突部分须明确提示。

## 1. 对象与身份

| 对象 | 关键语义 |
| --- | --- |
| Vault / Book | 账库、账簿稳定随机 ID、币种、精度与时区 |
| Account | 类型、名称、排序、归档；不以可变名称作为身份 |
| Category | 收入 / 支出类型、最多两级、归档；退款复用支出分类 |
| Transaction | 类型、正金额、业务日期、备注和账户变动，作为一个聚合 |
| Account Movement | 某交易对账户的有符号增减，不能脱离交易独立提交 |
| Revision | 前置版本、候选版本、删除状态与必要追踪 |
| Import Batch | 来源、映射、行身份、进度、可见性与撤销范围 |
| Sync Operation | 不可变操作身份、依赖、前置版本、确认与重试状态 |

业务 ID 随机生成，不包含账户名称、金额、日期或其公开 hash。第一版一个 Vault 只有一个 Book，但仍使用稳定 Book ID，避免日后用标题迁移身份。

## 2. 金额、日期与验证

- 金额按 CNY 的分存为有界 64 位整数；不使用浮点累计或隐式四舍五入。
- 跨语言 / 归档金额使用明确的十进制字符串，并验证范围、精度和格式；拒绝溢出和不明确的千位 / 小数分隔。
- 普通交易金额严格为正，类型决定资金方向；期初和差额调整的账户变动允许有符号整数。
- 转账要求不同账户、相同币种、金额一致；第一版不含手续费联动。
- 记账日期是用户选择的日历日期，不从 UTC 修改时间推导；创建 / 修改时间使用 UTC 追踪。
- 时区只影响“今天”等默认输入；更换设备时区不自动改写历史业务日期。
- 列表同日排序可以使用稳定次序，但设备时钟不决定并发修改胜负。

输入无效、账户归档、引用缺失、未来不支持格式等应返回具体错误。缺少引用的远端交易不得按零金额、默认账户或空类别悄悄应用。

## 3. 事件与报表

| 事件 | 例子 | 账户变动 | 月报 |
| --- | --- | --- | --- |
| 收入 | 工资 1000 元 | 收款账户 +100000 分 | 收入 +1000 元 |
| 支出 | 餐饮 30 元 | 付款账户 −3000 分 | 餐饮支出 +30 元 |
| 转账 | 银行转钱包 200 元 | 银行 −20000，钱包 +20000 分 | 不计收入或支出 |
| 信用卡消费 | 消费 100 元 | 信用卡 −10000 分 | 支出 +100 元 |
| 信用卡还款 | 银行还款 100 元 | 银行 −10000，信用卡 +10000 分 | 作为转账 |
| 普通退款 | 收到餐饮退款 20 元 | 实际收款账户 +2000 分 | 当期餐饮净支出 −20 元 |
| 期初 / 差额调整 | 补录余额 | 以显式调整事件记录差额 | 不计日常收支 |

退款按实际到账日期冲销当期支出，不能回写上月或计为当期收入。分类月净支出可以为负，界面保留真实数值。

第一版退款不要求绑定原消费，不能据此承诺自动检查累计退款是否超过原金额。关联消费、多次退款上限和并发退款将作为独立增强能力设计；届时必须有跨对象版本前置条件，不能仅凭本机总额检查。

公式：

```text
账户余额 = 所有本机有效交易对该账户的有符号变动之和
月净支出 = 月支出 − 月退款
月结余 = 月收入 − 月净支出
账簿净资产 = 所有账户有符号余额之和
资产 = 所有正余额之和
负债 = 所有负余额绝对值之和
```

信用卡欠款为负，溢缴为正。现金、钱包等出现负数时提示核对，不自动改零。第一版只有一个账簿；后续多账簿不能忽略真实资金账户重复建模的问题。

## 4. 原子性与有效版本

转账的双方变动属于同一个 Transaction payload，本地写入、同步、编辑、删除和恢复都作为整体操作。不得把两端当成两笔独立交易。

每个对象在本机投影中只有一个选中的有效版本。两端并发候选都保留，但不把它们都作为新增流水计入余额。冲突界面显示双方差异及余额影响，解决后生成一个基于最新状态的修订。

一端本地候选尚未确认时，允许继续查看其余额，并标记“含未同步修改”；发生冲突时，选中版本与待处理候选必须可追踪。服务端版本更改不能直接清除本地队列或历史。

业务事实更新与 outbox 写入使用同一数据库事务；远端应用与游标推进也使用同一事务。派生索引损坏可由事实重建，索引不成为新的同步事实。

## 5. 账户、分类与对账

账户和分类已有流水时默认归档而非硬删除。归档不影响历史余额与报表；新建交易不可选归档对象，旧交易仍能解释。

期初余额为专门事件，避免隐藏在账户字段与余额投影之间重复计算。修改期初余额会重算历史余额，应展示影响，不混入当月日常收入。

差额调整同时保存已观察余额、目标余额、计算差额、原因及观察版本。并发新增其他交易后，最终余额可能不再等于此前目标；不能用旧目标再次覆盖。界面提示重新对账，以固定差额事件为事实。

账户类型和币种存在历史约束。改名保留 ID；第一版不做账户合并和类别合并，修改已使用类别的收支类型须受限。

## 6. 删除、恢复与历史

删除产生新修订与同步删除标记，回收站保留可恢复内容。恢复是基于删除版本的新操作，不是移除 tombstone。

账户 / 分类归档、交易删除与账库删除是不同层级动作。删除交易后，余额按新有效状态重建，转账双方同时移除。

第一版不承诺永久保存全部编辑内容；历史保留与“彻底删除”须在同步与加密规格冻结时确定一致策略。删除标记、身份和必要防复活信息可在不保留账务明文的情况下长期保存。

## 7. 合成账务基线

以现金期初 100 元、银行卡期初 1000 元、信用卡期初 0 元为起点：

1. 银行工资收入 2000 元。
2. 银行转现金 200 元。
3. 现金餐饮支出 30 元。
4. 信用卡购物 100 元。
5. 银行还信用卡 100 元。
6. 现金收到餐饮退款 10 元。

结果必须为：现金 280 元、银行 2700 元、信用卡 0 元、净资产 2980 元；收入 2000 元、毛支出 130 元、退款 10 元、净支出 120 元、结余 1880 元。期初净资产 1100 元，加结余 1880 元等于期末净资产 2980 元。

这一基线应覆盖本地、同步、导出、恢复与迁移；跨月退款、转账删除、冲突和差额调整另有独立样例。测试须核对数值与事实集合，不只核对函数返回成功。
